# CUDA 分精度优化与数据流优化

创建：2026-10-07 09:49:49，Asia/Shanghai。状态：已完成实施与验收，未提交。

## 范围与基线

用户要求针对不同精度实施不同优化，并继续推进拼接 kernel 启动合并、减少
数据往返和 head-256 跟踪 attention 融合。沿用用户已经批准的独立快速模式
最终质量验收：默认 F32 保持原有数值合同；F16 快速模式允许中间张量不同，
最终检测、掩码、跟踪 ID、生命周期和状态边界仍需满足已有门限。

基线为上一轮已完成验收但尚未提交的工作区，不等同于 Git HEAD `0aa4971`。
在修改前保存完整源文件快照、工作区 diff 和二进制／CUDA 库身份；保留
`build/cuda-execution-optimized`、上一轮验收和性能记录，不原地重建或改写。
RTX 4090 上此前 F32 权重图像为默认 524.384 ms／快速 360.880 ms，视频
单对象 798.549／632.100 ms、四对象 1364.295／1164.533 ms 每帧。

## 实施步骤

1. 定位并合并连续布局 concat 的第四维 host launch 循环，保留 byte/half/
   float/64-bit 元素与量化 block 的逐字节拼接语义，以及第四维带 stride 的
   view。所有精度共享该无损优化，先做独立数值／边界测试，再跑 A/B/A。
2. 按 F32、F16、Q8_0、Q4_K 的实际算子形状筛选不同路径。F32 不降低
   累加精度；F16 评估 head-256 memory attention 的现有融合能力及必要的
   CuTe/CUTLASS 方案；量化路径检查 MMQ/cuBLAS dispatch 与 RHS staging，
   只有同精度收益可靠且质量通过才采用专用策略。
3. 梳理图像／检测／跟踪阶段的数据上传与下载，区分公共 API 必需输出和
   内部中间量；优先减少可证明冗余的传输。设备常驻方案必须同时满足缓存、
   多 session 所有权、图生命周期与峰值内存约束，不能隐式共享可变全局状态。
4. 实验以新的隔离目录运行，GPU 测试、计时和 profiling 串行。未通过边界
   检查、质量验收或没有稳定收益的候选保留失败记录，不合入默认路径。
5. 选定实现后更新 pinned GGML patch/tree identities、必要的量化凭据兼容项、
   backend 策略与相应回归。独立 clean CUDA Release 构建并做 CPU 回归。

- 同硬件／模型／输入做无 profiler A/B/A 筛选，单独记录原始样本、实际
  loader、环境和内存；随后以新生产构建进行正式计时与独立 Nsight 核查。

  共享和长序列 session；不得用算子小测试替代完整模型验收。
- 更新双语 benchmark 与 Unreleased，记录分精度选择、采用／放弃的候选、

  覆盖上一轮记录或新增依赖私有产物的文档链接。

### 算子与传输证据

`build/cuda-dataflow-profiling-v2` 包含六个图像 trace、各五个 warm 区间，分析为
`operator-analysis-v1.json` 和 `operator-comparison-v1.json`。这些带 profiler
的区间数据只解释算子，不替代正式端到端计时。

- 每次图像推理 concat 从 8,260 次降至 132 次，减少 98.40%。总 kernel 数
  dense 默认 16,112→7,984、全模块量化默认 16,718→8,590、dense 快速
  14,040→5,912、全模块量化快速 13,924→5,796。
- 全模块 Q8_0/Q4_K 默认模式的实际 H2D 为 156,833,656→140,636,024 bytes，
  49→43 次；D2H 为 183,383,972→183,178,148 bytes，11→10 次。新增一次
  204,800-byte 设备内 query 整理拷贝。CUDA 传输记录与库的 API 计数口径
  略有差别，两者均支持每次约 16.2 MB 的上传减少。
- 低 bit 仍不自动带来更快矩阵计算：快速模式 Q8_0 与 Q4_K 的 packed matrix
  kernel 合计分别约 22.94／23.69 ms，RHS staging 约 5.34／5.36 ms。其余布局、
  attention、逐点操作和阶段间等待仍占据大量时间，权重容量减少不能等价为
  相同倍数的端到端加速。

head-256 视频调用另外使用 `build/cuda-dataflow-video-profiling-v1` 的 32 帧
四对象快速模式前后对照，实际 loader 和输入身份单独绑定，不混入发布计时。

两份视频 trace 都成功完成，head-256 融合调用从 0 增至 992 次，总 kernel
数从 631,530 降至 276,202。首次计数正则遗漏了 Nsight 模板参数中的 `(int)`
标记，末尾断言失败；`analysis-v2.json` 修正名称解析并重新核对二进制、库、
输入、manifest 和原始 trace 的 SHA。没有重新运行或覆盖 trace，没有重评质量
门限，原失败记录仍保留。
