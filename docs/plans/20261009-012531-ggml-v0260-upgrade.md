# GGML v0.26.0 升级计划

创建：2026-10-09 01:25:31（Asia/Shanghai）。
状态：已完成用户确认的 Linux 实施与验证范围；Metal 硬件验证和完整 CPU 长序列留待后续。
SAM.cpp 基线：`30dd38b6d0da1a8308fa2627c4d07bd2d0dae1a1`；规划开始时工作区干净。

## 范围与推荐方案

把官方 GGML 从 v0.25.3 的 `353b63b439f27ab2cc19dac97ab1681ba6d2d084`
升级到 [v0.26.0](https://github.com/ggml-org/ggml/releases/tag/v0.26.0)，
继续按完整提交 `d7cb574130e6f01ad25b3289685489200febcd74` 锁定。
该 tag 是 annotated tag，tag 对象为 `d1b3faafa60f4628879eb49a2ee72dc71cab610a`；
`GIT_TAG` 使用前述解引用后的提交，避免混淆两种对象。

最小改法是替换版本号和 SHA，但它会被现有源码哈希校验拒绝，而且旧 Metal 补丁
包含已删除文件。因此推荐一次完整的依赖迁移：移植必要补丁，同步来源校验，
完成三后端与消费者验证后整体交付。以下步骤是同一可回退变更中的执行顺序，
不单独交付只能配置、不能运行的中间状态。

保留编译式 C++17 库、公共 API、共享模型图、GGUF schema、原权重及 tokenizer。
保持 `GGML_CUDA_GRAPHS=OFF`、现有默认算术和显式 CUDA F16 模式。
本次不引入新后端、BF16/FP4 模型支持、新公开配置或新的精度认证；
`gguf-py==0.19.0` 与参考环境锁文件不随 C++ GGML 自动升级。

工作量为中等规模依赖迁移，涉及超过 8 个文件；主要成本是 Metal 补丁移植和模型
回归。移除全部本地补丁的方案不采用：v0.26.0 仍未满足现有精度契约。

```text
固定 GGML 提交 -> 构建目录内源码副本 -> Metal/CUDA 补丁与哈希校验
                                      |
                              编译 GGML -> SAM 库与工具
                                      |
                           算术 / 模型 / 消费者验证
```

## 已核实的升级影响

| 范围 | 只读调查结果 | 实施决定 |
| --- | --- | --- |
| 版本与源码来源 | `cmake/ggml.cmake`、`cmake/prepare_ggml.cmake` 固定旧提交；prepare 同时固定原树、Metal-only 树、组合树及两个补丁哈希 | 保留完整校验、隔离副本和来源标记机制，重新生成全部对应身份 |
| Metal attention | 上游删除 `kernels/fa.metal`，改为 `fa_common.metal`、`fa_f32.metal`、`fa_vec_*` 等；新 `FA_TYPES_F32` 的 Query 仍为 half | 把 float Query、共享内存偏移和 host 分配量移植到新布局，保留 head 32/64 的明确边界 |
| Metal 补丁应用 | 9 个旧目标中 `fa.metal` 消失；`ggml-metal-device.m` 和 `ggml-metal-ops.cpp` 各有一段旧上下文不匹配 | 重新生成补丁，检查按 dtype 拆分后的库发现、kernel 命名和精度分派；不能只刷新哈希 |
| Metal 小矩阵 | 新 few-row MMA 路径在普通 matrix 路径之前分派；F32/F16 generic 实现使用 float 矩阵运算 | 保留该上游路径，补充 3–16 行和分派边界数值覆盖；不预先禁用优化 |
| CUDA | `ggml-cuda.cu` 的 cuBLAS 类型选择与 dense dispatch 两段旧补丁上下文变化；新的薄矩阵 MMVF 分派需覆盖 | 将显式 F32/F16 分支放到正确的分派位置，保留 pedantic F32、环境变量不能覆盖显式精度、attention/window/concat/copy 契约 |
| CUDA copy | 上游为旧转置快路径增加目标 contiguous 条件；本地 copy 优化的旧 hunk 上下文仍存在 | 保留上游修复，复核本地快路径只接受它声明的 dense 目标；运行 stride、padding 和原始位模式回归 |
| API / scheduler | `ggml.h`、`gguf.h` 在两个 tag 间无差异；scheduler 六参数接口保留。新增 multi-buffer 接口，`ggml_set_input` 新增 `GGML_OP_NONE` 断言 | 不为新增 API 改造 SAM；现有直接 input 调用均来自新建 tensor，继续用构建、workspace 和会话测试验证语义 |
| GGUF / 分配 | 上游加强 GGUF 大小和整数溢出检查，并调整 context tensor 分配实现 | 保留 SAM 的有界 reader 和模型 schema 校验，复跑 malformed GGUF、权重分配和内存统计测试 |
| 量化来源 | `tools/CMakeLists.txt`、converter、validator 和 Python fixtures 固定旧版本；旧 K-quant GGUF 的 sidecar 记录真实旧构建 | 分开管理当前生成器身份与历史模型来源白名单，避免新 validator 错误拒绝已有模型 |
| 量化编码 | `make_qkx3_quants` 修改候选值截断/舍入处理 | 不承诺新旧 K-quant 编码逐字节相同；分别验证旧文件可读、新编码合法和模型输出 |

补丁调查为内存中的旧 hunk 上下文匹配，不是 `git apply --check` 或编译结果。
CUDA 补丁新增的 `sam-precise.cu/.cuh` 在上游不存在属于正常新增文件。

关键上游依据：
[Metal F32 attention](https://github.com/ggml-org/ggml/blob/d7cb574130e6f01ad25b3289685489200febcd74/src/ggml-metal/kernels/fa_f32.metal)、
[Metal 公共 attention 布局](https://github.com/ggml-org/ggml/blob/d7cb574130e6f01ad25b3289685489200febcd74/src/ggml-metal/kernels/fa_common.metal)、
[CUDA 分派](https://github.com/ggml-org/ggml/blob/d7cb574130e6f01ad25b3289685489200febcd74/src/ggml-cuda/ggml-cuda.cu)、
[量化编码变更](https://github.com/ggml-org/ggml/commit/c30612b)。
本地契约以 [补丁说明](../../cmake/patches/README.md)、
[现行构建](../../cmake/ggml.cmake) 和 [模型验证](../validation.md) 为准；
[上次 GGML 迁移](20260930-231832-upstream-ggml-0253.md) 仅作为历史依据。

## 实施步骤

1. **固定基线和隔离工作目录。** 记录 SAM 提交、原 GGML/补丁身份、工具链与硬件。
   从共享仓库的 Git 对象导出新提交到 `build/ggml-v0260/upstream/`；不 checkout、
   修改或打补丁到共享仓库。旧构建和数值回执保持只读。实施时先复核工作区变化；
   本计划中的本地路径仅表示本机可用输入，不随源码分发。
2. **移植 Metal 补丁。** 在新的源码副本中保留 precise dense、head 32/64 float Query
   attention 和原生 window。把 Query 类型相关偏移放到 `fa_common.metal`，把限定
   head 的实例化放到 `fa_f32.metal`；默认、其他 head 和量化实例保持原语义。
   同步 `ggml-metal-device.m` 的 host 精度选择、`ggml-metal-ops.cpp` 的共享内存
   和 vector/sparse-hint 分派。核对 embedded 构建及具备工具链时的独立 metallib。
   保留 M4 的已验证范围，tensor API 分支另列硬件覆盖结果。
3. **移植 CUDA 补丁。** 在上游 v0.26.0 分派基础上恢复必要精度分支，不覆盖新增
   BF16/NVFP4 等无关上游逻辑。保留显式 F32 优先级、F16 输入/F32 累加、分组且
   限定 scratch 的 precise attention、全 mask 行零输出、原生 window 及 copy/concat
   优化。重新应用并检查上游非连续目标修复。只有同操作数数值测试证明等价时才
   删除已被上游替代的 hunk。
4. **冻结依赖身份。** 更新 `cmake/ggml.cmake`、`cmake/prepare_ggml.cmake` 和
   `cmake/check_ggml.cpp`；从干净原树依次生成 Metal-only 和组合树，实际计算三种
   tree SHA-256、两个补丁 SHA-256、全部 touched-file 前后哈希。同步 revision
   拒绝提示、`.sam-precision-provenance`、fingerprint 和 `GGML_BUILD_COMMIT`。
   `sam_prepare_ggml` 仍接受该版本三种已验证树，拒绝旧版本与未知内容。
   CPU 配置也会准备两个补丁，故补丁与 pin 必须在同一候选变更内更新。
5. **迁移生成器与历史来源校验。** 更新 `tools/CMakeLists.txt`、
   `tools/convert/convert_sam3.py`、`tools/convert/sam3_gguf.py`、
   `tools/validation/validate_image.py` 及对应两个 Python 测试文件。
   新转换只接受新 pin 的实际 helper/library 身份。旧模型校验按
   `(ggml_revision, ggml_version, ggml_build_commit)` 完整组合保留已认可的
   v0.25.3 来源，包括旧原版、Metal-only、当前组合补丁和已有四个历史组合。
   白名单放在现有 `sam3_gguf.py` 中供工具共用；不接受任意版本或拼接字段。
   sidecar 原值、权重字节、hash 和历史回执不改写为 v0.26.0。
6. **执行下述验证。** 先源码准备/API/CPU，再 CUDA 和 Metal 算术与模型回归，
   最后消费者与性能检查。只在新分派、来源兼容或现有测试缺口需要时补行为测试，
   重点扩展 `tests/runtime/ggml/test_precision.cpp`、
   `tests/runtime/ggml/test_cuda_copy.cpp` 和
   `tests/integration/test_prepare_ggml.cmake`。
7. **交付与结果记录。** 同步 `README.md`、`THIRD_PARTY_NOTICES.md`、
   `cmake/patches/README.md`、`docs/architecture.md`、`docs/gguf.md` 的当前依赖信息；
   保留 MIT 与窗口实现的原归属。实现完成后在 `changelog.md` 的
   `Unreleased/Changed` 记录升级及旧 GGUF 兼容性。本计划追加真实检查、差异和
   未覆盖硬件，不批量替换历史计划里的旧版本，不覆盖不可变报告。

历史上已失败或未获认证的精度配置保持原状态；不能为了本次升级修改冻结门槛。

[证据边界](20261007-200954-precision-acceptance-gates-v2.md)。

或峰值内存若增加超过 5%，在空闲设备复测并定位分派/分配变化，作为本次升级的
回归调查触发线。未解释的持续退化不切换默认 pin；这不是改写历史数值门槛。

## 环境、风险与回退

已只读确认：本机 Linux x86_64、RTX 4090（compute capability 8.9，24564 MiB）、
驱动 610.57.04、CUDA 13.3、CMake 4.2.3；Git/C++/CTest/Ninja 和
`.venv-reference/bin/python` 可用。共享 GGML 仓库已有目标 tag，HEAD 仍是旧 pin，
工作区干净；官方 tag 的远端访问成功。`models/` 中已有 F32/F16、两类四种量化模型、
F32/hybrid 视频模型及原始/decoded reference 目录；实施时还要核验其 manifest 和
内容 hash。本次没有运行模型，也没有将“文件存在”记作数值验证通过。

最脆弱的前提是 Metal 补丁在拆分内核后仍正确分派并保持数值契约。本机没有
`xcrun` 或 Apple GPU；实施负责人需要在可用 Apple GPU 主机完成该验收。
硬件未就绪时可以完成候选变更和 CPU/CUDA 证据，但默认升级的交付保持待验收，
不能用旧版 M4 回执证明新版本通过。tensor API 的未覆盖部分继续明确标注。

本次无需新增 API key、第三方账号或服务；使用已有合法 checkpoint 与参考输入，
不触发新模型下载。源码服务不可用时使用本地固定对象和哈希校验。
attention 的 tile/scratch 上限继续保持，长序列与大 key 数回归用于排除规模增长
造成的工作区失控，不扩大默认 batch 或视频状态预算。

回退以整个升级变更为单位恢复旧 SHA、补丁、来源规则和工具身份，再使用保留的
旧构建或从旧 pin 重建。旧 GGUF 与 manifest 不需要数据迁移；新编码文件另存。
每个完成的构建/验证周期后清理本次无用中间副本、失败编译产物和重复 dump，保留

reference 的诊断结果；显式 F16 计算沿用最终输出质量门槛，不宣称全部中间

在所有数值回归结束后串行执行。以下均为本次实测，不替换既有性能页中的旧回执。

`66731fa5def347677f78d7422b81979be0f8e2f7ead941db9a466d1cfa715120`）、
