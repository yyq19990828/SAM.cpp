# CUDA 后端实施计划

创建：2026-10-06 21:57:22，Asia/Shanghai。状态：已完成，阶段 0–4 的实现、原始权重验收、共享会话、完整性能测量与交付审计均已完成；本次 CUDA 硬件验证范围为 Linux x86_64 RTX 4090。
源码基线：`54b1df7`；本次开始时工作区干净。

## 目标与交付范围

在现有 GGML 运行时中增加 CUDA 驱动，复用 SAM 3 图像及视频计算图，保持
C++17/header-only 集成、GGUF 格式、模型精度与 session 所有权契约。
首个验证平台是本机 Linux x86_64 + NVIDIA RTX 4090；支持结论按任务和权重
profile 分阶段形成。单机通过不代表 Windows、Jetson 或其他 GPU 已验证。

最小可交付版本是显式 CUDA 的 SAM 3 F32、mixed F16/F32 图像推理，包含
设备选择、真实调度统计、完整原始权重对照和可复现构建。视频 F32/hybrid
和图像量化分别作为后续交付；前一阶段可独立使用。规划期间仅新增本文件，
实现完成后再维护 `changelog.md` 的 Unreleased 和对应支持文档。

首版只在一个可见 CUDA 设备上执行。多 GPU 切分、NCCL、模型并行、TensorRT、
自建 allocator、异步公开 API、独立 CUDA 模型图、其他 SAM 家族和性能融合
不进入首版。CUDA Graph capture 与量化 kernel 调优在正确性通过后单独评估。

## 已核对的基础

| 项目 | 当前状态 | 对实施的影响 |
| --- | --- | --- |
| 公共接口 | `Backend` 只有 Auto/Cpu/Metal；`BackendOptions` 有 backend/threads | 追加 CUDA 枚举与设备选项；保留旧聚合初始化的字段顺序 |
| 驱动边界 | `BackendDriver` 管理 handle、F16 promotion、node counter | 在 `backends/cuda.hpp` 实现注册表发现、初始化和精度策略 |

## 必须前置解决的算子与精度问题

核对固定版本的 [CUDA 算子支持与实现](https://github.com/ggml-org/ggml/blob/353b63b439f27ab2cc19dac97ab1681ba6d2d084/src/ggml-cuda/ggml-cuda.cu)
和 [Flash Attention 分派](https://github.com/ggml-org/ggml/blob/353b63b439f27ab2cc19dac97ab1681ba6d2d084/src/ggml-cuda/fattn.cu)
后，首版不能仅增加枚举和驱动：

1. CUDA 后端没有 `WIN_PART`/`WIN_UNPART` 支持入口，SAM 3 ViT 直接使用两者。
   需要补齐原生 CUDA 实现；早期 CPU 回退只能用于定位，不能作为完整 CUDA 验收。
2. Flash Attention 的 head 分派没有 32 维分支，而 SAM 3 detector/空 geometry
   路径及现有精度测试需要 head 32。需要明确补齐支持或选用经过验证的等价执行实现。
3. CUDA attention 分派不能从当前代码直接得到本项目要求的 F32 保证。
   矩阵 cuBLAS 路径存在 F32 precision 分支及环境覆盖；还需覆盖其他矩阵分派。
   源码风险不等于实测误差，必须通过直接设备探针定论。

优先在固定 GGML 的后端层补齐窗口操作及 head-32/64 的 F32 attention，
让模型继续使用相同图。窗口只搬运 F32 元素，严格保留通道/window 顺序、
边缘零填充、裁剪和支持谓词；初版限制为已验证的连续布局，并检查索引边界。
attention 保持 mask、scale、softmax 分母、batch/head 隔离与 F32 输出。
可先采用正确且工作区有界的 CUDA 实现，融合优化随后独立测量。

若原生 attention 补齐代价过大，备选是由 runtime 的已验证能力策略选择
共享的 F32 分块 matmul/softmax 图。模型不得按 CUDA 名称分支；该方案须另记
图容量、工作区、数值与性能结果，不能构造完整 5184×5184×heads 的无界中间量。
保留当前 tracker 256 维 tiled attention；本任务不顺带将其替换为 flash kernel。

## 公共行为与运行时设计

- 在 `Backend` 末尾追加 `Cuda`，在 `BackendOptions` 末尾追加
  `int cuda_device = 0`，在 `RuntimeStats` 末尾追加 `cuda_nodes`。
  保留原有枚举值、字段顺序、`{Backend::Cpu, 4}` 及旧统计聚合初始化。
- `cuda_device` 表示 CUDA 注册表的可见设备序号，受 `CUDA_VISIBLE_DEVICES`
  的可见性/重排影响；它不是 PCI 编号。非 CUDA 请求使用默认值 0，拒绝负数
  及非 CUDA 请求的非默认设备值。越界设备在初始化前明确报错。
- 图像/视频 CLI 增加 `--backend cuda`、`--cuda-device N`；帮助、解析、错误、
  JSON backend 名称及 runtime 统计同步更新。报告实际设备名称、逻辑序号和
  运行环境，首版不为此新增通用公开设备管理框架。
- `make_cuda_backend` 只从 CUDA 注册表选设备，使用通用 GGML device/init API
  和现有 RAII；SAM 头文件不直接依赖 CUDA Toolkit 头文件或库 API。
  无 CUDA 编译、无可见 GPU、错误序号、初始化/精度失败分别给出可诊断错误。
- 首版保持当前 Auto 选择：F32 和量化走 CPU，F16 在可用时走兼容 Metal。
  CUDA 通过显式请求启用；自动选择 CUDA 是后续独立行为变更，需要 profile
  验收、优先级规则与用户文档，不能随增加驱动悄悄改变默认结果。
- CUDA 保留 F16 权重存储的候选策略必须通过 F16×F32 探针；算术遵守现有
  F32 要求。若某路径不能满足要求，明确拒绝或使用经验证的设备内 promotion，
  并记录实际权重/工作区成本。视频 BF16 feature/memory 和 F16 输入舍入仍属于模型。
- 显式 CUDA 的完整验收要求实际计算节点在 CUDA，`cuda_nodes > 0`，
  `cpu_nodes == blas_nodes == metal_nodes == 0`。数据上传、下载及 host
  后处理不属于 CPU 图计算节点。早期允许回退的诊断构建必须单独标记。
- 将目前仅限量化 Metal 的严格放置检查收敛为小型运行时执行策略，保留现有
  Metal 行为；生产 CUDA profile 在分配前检查支持，在调度分配后、compute
  前检查实际放置，无法满足时在执行前报错。CPU 可以继续作为 scheduler 的
  必要尾项，但执行错误和 OOM
  不自动重试另一个设备。不引入公开的“忽略精度/回退”开关。
- CUDA 节点按 runtime 拥有的 backend handle 归属计数；未知/外部/null handle
  仍报错。记录权重与 workspace 分配、分区、传输量；RSS 与 GPU 显存分开报告。
  当前 upload/download 字节不是完整 PCIe 流量，不能由它们推算所有设备间复制。

## 分阶段实施与验收

### 阶段 0：构建、算子和精度可行性

预计 1–2 个工程日完成基线调查；原生窗口与 attention 补齐另外预留 3–7 日，
最终由探针缺口决定。这是估计，不是交付日期。

1. 使用独立 `build/cuda-probe`，固定依赖、Release、`GGML_CUDA=ON`、
   `GGML_METAL=OFF`、`CMAKE_CUDA_ARCHITECTURES=89`，先做最小编译/设备初始化。
   核对 CUDA Toolkit、驱动、host compiler 和系统链接依赖，不能靠
   `--allow-unsupported-compiler` 掩盖兼容问题。
2. 从图像和视频实际图列出 operator/type/shape/stride/mask 矩阵，包含窗口、
   F32 im2col/convolution、转置卷积、pool/interpolation、RoPE 的共享基础运算、
   gather/concat、norm/softmax、矩阵和 attention；不要只测理想方阵。
3. 将现有 precision/window 测试参数化到选定设备，直接分配到 CUDA 并调用
   `ggml_backend_graph_compute`，避免 scheduler 回退让探针误通过。窗口结果
   与 CPU/手写 goldens 完全一致；精度探针沿用原有门槛，覆盖 F32/F16 左矩阵、
   batch/transposed/tail，以及 head 32/64、短 query、5184 keys、mask 和尾部。
4. 检查 TF32、F16/BF16 staging、`GGML_CUDA_CUBLAS_COMPUTE_TYPE` 等精度覆盖，
   以及 attention 隐式 K/V 转换；记录已验证设置。不能依靠全局环境变量修改
   调用方进程来维持库契约；不兼容的外部配置应由能力/精度检查明确拒绝。
5. 如需补丁，在 build-local 源码应用独立 CUDA patch，保留 Metal patch 内容，
   固定应用顺序、patch SHA-256、原始/最终 tree hash、许可证和修复记录。
   更新 `prepare_ggml.cmake` 的组合校验及回归；不修改共享 upstream checkout。

退出条件：明确可编译工具链，完成真实 CUDA direct probes，所有已知缺口有
通过测试的解决路径。未通过前不推进全模型性能宣传或量化验证。

### 阶段 1：驱动、配置和集成

预计 1–2 个工程日，依赖阶段 0。

修改 `types.hpp`、`internal/input_validation.hpp`、新 `backends/cuda.hpp`、
GGML `backend.hpp/runtime.hpp/graph.hpp/workspace.hpp` 中实际需要的策略点，
以及 `examples/image_support.hpp`、图像/视频 CLI 和 `tests/CMakeLists.txt`。
保持 CPU/BLAS 排序、header-only、独立头文件和 two-TU linkage。

测试显式选择、旧聚合初始化、非法序号、不可见设备、缺失注册表、初始化失败、
实际 GPU 权重矩阵归属、未知 backend、回退拒绝、buffer 释放和跨 runtime 隔离。
用真实 GPU buffer affinity 测调度；host-input-only 图会受 GGML 的 CPU 输入
分配规则影响，不能用该图替代 CUDA 权重路径证明。

CUDA-disabled 构建不需要 NVCC/CUDA 头文件；CUDA-enabled 无 GPU 的环境仍跑
CPU/接口测试，设备执行项明确 skip。GPU 验收作业必须要求 CUDA 测试实际执行，
不能把所有设备项 skip 后的绿色 CTest 当支持证明。扩展 caller-owned GGML
consumer，验证复用单一 runtime 和精度能力，不能只相信宿主 target 名称。

退出条件：CPU 回归通过，真实 CUDA 权重/graph/workspace 测试通过；原有 Auto、
显式 CPU/Metal 的契约保持。Metal 回归在 Apple 硬件执行并单独记录。

### 阶段 2：完整图像推理（首版交付）

预计 2–3 个工程日加完整对照时间，依赖阶段 1。

- 扩展 `validate_image.py`、CLI tests、session/graph/RoPE/precision/window tests
  及 `SAM_REFERENCE_BACKEND` 的 CUDA 参数、统计和放置检查。
- 使用原始 Meta checkpoint 转出的 F32、mixed F16/F32 GGUF，固定 tokenizer、
  解码后的输入像素和完整 `sam3-image-cases.json`，对照官方中间 tensor、
  mask、score、box、负 prompt、裁剪/缩放和输出所有权，沿用冻结 gates。
- 验证图像/text cache、图像替换、重复推理、多个 session 共享权重、异常后
  重置；所有支持结论绑定真实设备放置，不接受只报告 CUDA 权重的 CPU 执行。
- 阶段 3 前显式拒绝尚未验证的 CUDA 量化组合，错误发生在权重分配之前；
  不让现有量化非 CPU 分支自动产生未经验证的 arithmetic profile。
- 完成同机 CPU/CUDA 的原始 truck 协议：一次 cold call + 五次完整未缓存
  图像调用，cache hit 单列。统计模型加载、端到端推理、GPU 峰值与 RSS；
  GPU 同步边界明确，不能用 submit 时间代表执行耗时。

退出条件：两个图像 profile 的完整 reference receipts、Release tests 和
首个 RTX 4090 benchmark 齐全。公开文档只声明已通过的任务/profile/环境。

### 阶段 3：完整视频 F32/hybrid

预计 2–4 个工程日加完整对照时间，可在图像首版交付后进行。

扩展 `validate_video.py`、`benchmark_video.py`、video session/long-session
测试中的 CUDA 选择与统计；修正 benchmark 现有“另一个 backend 只有 CPU/Metal”
假设，检查所有非目标设备计数，保持历史 CPU/Metal receipts 可读。

在完整官方五 case/216 帧语料验收进入对象、遮挡、消失/重现、birth ID、
association、memory selection、输出延迟和最终 drain。分别执行 F32/hybrid，
保留 F16 输入、BF16 feature/memory、F32 pointer 的模型舍入边界。
增加既有缓存图在离散显存上的重绑定、shape 切换、对象 batch、frame release、
session reset 与 64+64 帧 session 交错测试，检查显存不随帧数无界增长。

官方 CPU oracle 仍可作为固定参考；如另导出官方 CUDA 对照，必须单独记录
torch/TF32/autocast/舍入/输入 provenance，不能覆盖历史参考。当前视频导出器
仅允许 CPU，迁移 oracle 不是实现 CUDA 推理的前提。

退出条件：每个视频 profile 完整数值/session 验收、无 CPU compute fallback，
再跑单/四对象 64 帧、16 warmup + 48 measured 的 median/p95/最终 drain 协议。

### 阶段 4：图像量化与性能优化

量化预计 2–4 个工程日加完整对照；性能优化按测量另立计划。

先验证 vision/full-component Q8_0，再验证 Q6_K、Q5_K、Q4_K；CUDA
resident 权重保持原 GGUF packing，逐一测试 native quantized 矩阵的实际
staging、累加、工作区和放置。使用对应原始 oracle 与冻结 output-quality/
tensor-fidelity gates，不把 CPU-F32 或 Metal 的 arithmetic receipt 冒用为 CUDA。

为 CUDA 定义经过验证的算术 profile；即使复用已有名称，也须证实其全部
语义并在 validator 中显式授权。`validate_image.py` 的 allowed profiles、
quantization receipts、`tools/test_quantization_tools.py` 同步扩展，保留
历史证据的校验行为。schema-4 自定义模块组合继续作为诊断范围，不能因 CUDA
启用就扩展为全部组合已验收。量化视频不进入本阶段。

数值通过后按 stage/kernel/transfer profiling 决定是否启用 CUDA Graphs、
批处理、驻留优化或融合 attention。每个优化用匹配 A/B/A 比较，计入布局转换、
传输、同步及 allocation；不预承诺相对 M4 Pro 的倍数提升。

## 构建与验证入口（实施后执行）

保持标准构建开启测试和示例，不额外引入 `SAM_CUDA` 开关。
使用固定 GGML 的 [CUDA CMake 集成](https://github.com/ggml-org/ggml/blob/353b63b439f27ab2cc19dac97ab1681ba6d2d084/src/ggml-cuda/CMakeLists.txt)
及 `sam::sam` 传递链接；首个 89 架构配置只针对本机，发行构建另列实际支持的
架构与编译器矩阵。[NVIDIA CUDA 发布说明](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html)
用于实施时核对工具链要求，具体版本以本地编译记录为准。

```sh
rtk proxy cmake -S . -B build/cuda-cpu-regression -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=OFF -DGGML_METAL=OFF -DGGML_BLAS=OFF
rtk proxy cmake --build build/cuda-cpu-regression --parallel 2
rtk proxy ctest --test-dir build/cuda-cpu-regression --output-on-failure

rtk proxy cmake -S . -B build/cuda -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON -DGGML_METAL=OFF -DCMAKE_CUDA_ARCHITECTURES=89
rtk proxy cmake --build build/cuda --parallel 2
rtk proxy ctest --test-dir build/cuda --output-on-failure

rtk proxy .venv-reference/bin/python tools/test_tools.py
rtk proxy python3 tools/check_docs.py
rtk proxy git diff --check
```

原始权重、完整 references、模型数值/session/benchmark 命令沿用
[验收流程](../validation.md)，实施时在新目录记录具体命令和 receipt。
另外运行 CUDA caller-owned consumer、CPU/BLAS 以及 Apple Metal 回归；本机
无法执行的硬件项明确记未验证，不由 CPU 通过替代。设备隐藏/无 GPU 及非法
index 场景在独立进程验证；真实多卡选择在有多卡的设备上补测。

构建和基准串行安排，计时期间不并发编译/推理。记录 checkpoint/GGUF/profile、
源码及补丁版本、编译参数、GPU/驱动/Toolkit/CPU/threads、完整 workload、
median/p95、cold/cache、同步口径、RSS、权重/workspace 和 GPU 峰值。
GPU 峰值需说明采样周期与局限，不能把 `nvidia-smi` 单次读数当精确峰值。
硬件支持、数值验收和性能收益分别形成结论。

权重、私有媒体、reference exports 和生成输出继续放在 ignored models/build；
只保存可再分发 fixtures 与必要的机器可读验收 evidence，链接到本计划。
缺少权重时优先使用认证的 Hugging Face 工具，分别检查认证与许可，不在聊天
请求 token。既有 machine-readable evidence 不改写。

## 主要风险与停止条件

| 风险 | 处理及阶段边界 |
| --- | --- |
| 固定 GGML 缺窗口/head-32 支持 | 阶段 0 完成 direct probes 和最小后端补丁；构建成功不足以退出 |
| F32 设置仍走降低精度的内核 | 覆盖真实分派及外部配置；不放宽现有数值 gates |
| 精确 attention 工作区过大 | 使用有界 tiling，记录额外显存；达不到预算先修复，不能隐式 CPU 重试 |
| 新增补丁使依赖校验失效 | 保持固定来源，验证 patch 组合、tree hashes、宿主 target 和 CPU/Metal 回归 |
